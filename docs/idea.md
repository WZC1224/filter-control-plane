# 内部筛选控制台（暂名）

> 状态：已确认（方向 1：A∩C，H 降级为远期）  
> 确认日期：2026-07-30

## Problem Statement

我们如何让业务/运营在一个新入口完成筛选主路径（下任务 → 跟进度 → 取结果），把 `data818` / `data-center-backend` 当下游能力，而不是再造第三套筛选中心？

## Recommended Direction

做 **运营任务工作台 + 薄控制平面**：

- 新 Flask 服务负责任务编排、状态汇总、权限与结果入口
- 通过适配器调用现有筛选 API，**不重写**筛号引擎
- 「数据中台」（多域、血缘、自助分析）只作为远期叙事与目录预留，**不进 MVP**

目标用户：公司内部业务/运营（第一优先级）。

成功标准：

- 运营主路径不再在 `data818` / `data-center` 两套后台之间来回切
- 旧服务当 API/任务下游继续跑
- 一个人、延续 Flask，先交付可日常用的 MVP

## Key Assumptions to Validate

- [ ] 运营愿意换到新入口 —— 找 1 人试用主路径
- [ ] 单下游（优先 `data818`）足够跑通 —— MVP 只接一家
- [ ] 任务状态能从现有 API/库可靠汇总 —— 先对一遍现有 order/task 接口

## MVP Scope

**做：**

- 内部登录
- 建任务
- 任务列表 / 状态（默认首页：任务列表 + 新建）
- 结果下载或链接
- 一个 `data818` 适配器

**技术约束：** 一人维护；延续现有 Flask 体系；另起新仓库/目录，不在旧项目里硬改成「第三套平行逻辑」。

## Not Doing (and Why)

- 完整数据中台（数仓 / 血缘 / 自助 SQL）—— 一人成本与运营价值不匹配
- 重写筛号引擎 / 合并两套后端代码 —— 违背「旧系统当下游」
- Day1 双系统适配 + 商品 / 充值 / 复杂菜单迁移 —— 稀释主路径验证
- 对外 ToB 售卖形态 —— 明确为内部使用
